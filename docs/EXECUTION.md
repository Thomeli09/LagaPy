# Running Lagamine executables

LagaPy uses **only `subprocess.run`** to launch the installed Prepro and
Lagamine executables. No GUI automation or extra execution dependency is used.
Prepro/Lagamine binaries are external, and LagaPy does not distribute them.

## Supported operations

| Operation | Python call | Executable arguments |
|---|---|---|
| Preprocess | `runner.preprocess()` | `Prepro.exe case.LAG x` |
| Solve | `runner.run()` | `Lagamine.exe case.DAT case.LAG x` |
| Both | `runner.run_all()` | Preprocess, then solve |
| Generate Windows batch file | `runner.write_batch_file()` | Same commands in a `.bat` file |

The final `x` follows the original scripts. Supply a different value through
`confirmation=` only if your Lagamine executable requires it.

## Run a case

```python
import logging

from lagapy.logging import configure_logging
from lagapy.solver import LagamineRunner

configure_logging(
    console_level=logging.INFO,
    output="logs/case.log",
    file_level=logging.DEBUG,
)

runner = LagamineRunner(
    lag_file="case.LAG",
    dat_file="case.DAT",  # May be generated by Prepro.
    preprocessor=r"C:\LagaProgs\Prepro.exe",
    solver=r"C:\LagaProgs\Lagamine.exe",
    working_directory=r"C:\Simulations\case01",
)

runner.run_all(timeout=None)
# Or run each separately:
# runner.preprocess(timeout=300)
# runner.run(timeout=None)
```

Absolute paths work directly; relative file/executable paths are resolved
against `working_directory` if provided. Otherwise, the `.LAG` file's
parent is used as the subprocess work directory. LagaPy does not change
Python's own current working directory.

Only the executable and inputs required by the operation are checked:
`.LAG` for Prepro; `.DAT` and `.LAG` for Lagamine. `.DAT` does **not**
need to exist before preprocessing. Companion files and generated results
are not prevalidated. The external solver may still need them.

Python raises `FileNotFoundError` for missing required files, `ValueError`
for unset configuration, `subprocess.CalledProcessError` for failed processes,
and `subprocess.TimeoutExpired` for timeouts. Exceptions are logged and
re-raised. `run_all(timeout=...)` applies the timeout to each stage separately.
A successful process exit is not proof of FEM convergence.

## Logging: independent console and file levels

`configure_logging()` configures the **`lagapy` logger**, without changing
the root logger or the configuration of an embedding application.

```python
import logging
from lagapy.logging import configure_logging

# Recommended: concise console output, detailed on-disk diagnostics.
configure_logging(
    console_level=logging.INFO,
    file_level=logging.DEBUG,
    output="logs/lagapy.log",
)

# File only:
configure_logging(console_level=None, output="logs/lagapy.log")

# Console only:
configure_logging(console_level=logging.WARNING)
```

`logging.DEBUG` < `logging.INFO` < `logging.WARNING` < `logging.ERROR`
< `logging.CRITICAL`. Each handler filters independently; the shared
logger automatically takes the lowest enabled level. The console handler
writes to **stderr**. Reconfiguring replaces handlers to prevent duplicate
lines. Log files use `RotatingFileHandler` in **append mode** (`mode="a"`),
with defaults of 5 MB per file and 3 backups. Configure this using
`max_bytes=` and `backup_count=`. For one log per case, give each case
its own output path.

### What about text printed by Lagamine?

**LagaPy's logging messages are separate from a subprocess's stdout/stderr.**
By default `subprocess.run` leaves the executable's stdout/stderr attached
to the parent process, so its output appears in the console without buffering
potentially massive simulation logs in Python memory. That output does not
flow through the LagaPy logger or into `logs/lagapy.log`.

For small runs, output can optionally be captured (but not simultaneously
inherited):

```python
result = runner.preprocess(capture_output=True)
print(result.stdout)
print(result.stderr)
```

`capture_output=True` buffers subprocess output in memory, so avoid it for
long, verbose FEM runs. If the executable's *own* output needs a permanent
record, prefer the solver's native output files; redirecting its stdout/stderr
or providing a streaming tee would be a separate execution feature.

## Windows batch scripts

```python
runner.write_batch_file("prepro.bat", solve=False)
runner.write_batch_file("solver.bat", preprocess=False)
runner.write_batch_file("both.bat")
```

Batch generation checks that selected configuration paths are provided, but
does not require the files to exist yet. Scripts quote filenames and exit
on the first failed command. They should be validated on the Windows target
before relying on their character encoding and argument handling.

## Tests and actual solver validation

Tests use mocked subprocess calls and a small synthetic POSIX executable.
They confirm invocation, error handling, working directories and basic file
flow, **not** Lagamine's physical or numerical correctness. Integration tests
against licensed Lagamine binaries remain to be done.
